# 一致性优先的桌宠动画资产管线

## 状态

- 阶段：Accepted
- 日期：2026-07-12
- 范围：Comet 宠物动画资产、播放协议与验收工具

## 背景

当前实现为 15 个状态各生成一张 4×4 宫格，再切为 16 张透明 PNG。切片工具通过背景去除、锚点对齐、共用裁剪窗口和体型归一化消除整体漂移，运行时以 Canvas 按固定 FPS 播放，并叠加少量 CSS 微动画。

这条管线适合快速覆盖大量状态，但 16 个格子本质上是 AI 独立重绘的 16 张图片。后处理可以修正画布位置和尺度，无法修正眼距、口鼻、毛发轮廓、肢体长度、道具形状和步态拓扑的变化。增加帧数或对不连续源帧插帧只会放大这些变化。

## 决策

采用“单一角色模型 + 少量关键姿势 + 确定性程序动画”的混合方案，保留现有状态机、Canvas、窗口位移与像素命中逻辑，渐进替换资产表达方式。

AI 负责提供少量经过验收的姿势，代码负责时间、位移、旋转、缩放、眨眼、呼吸、尾巴、道具和特效。不得为了凑固定帧数让 AI 重绘无必要的中间帧。

### 角色单一事实源

角色身份按以下优先级锁定：

1. 主人原狗照片；
2. 由原狗照片确认过的标准正面、侧面 reference；
3. `assets-src/template-grid-pixar.png`；
4. 已验收状态中的标准帧。

历史 Live2D 尝试中已经拆分的 reference、头、眼、闭眼、耳、身体、腿和尾巴，可复用为程序动画部件，但不恢复 Live2D/Cubism 运行时。新增 AI 资产必须以角色 reference 作为图像输入，采用编辑或参考生成；仅用文字描述生成的相似泰迪不得进入正式资产。

### 三种动画表达

运行时 manifest 支持以下类型，并允许旧 sequence 在迁移期间继续工作：

```ts
type AnimationAsset =
  | { kind: "sequence"; frames: string[]; fps: number }
  | { kind: "pose"; image: string; motion: MotionSpec; layers?: LayerSpec[] }
  | { kind: "keyframes"; poses: PoseFrame[]; loop: boolean };
```

- `sequence`：只用于确实需要连续肢体运动、且已经通过连贯性验收的帧序列。
- `pose`：一张标准底图加确定性运动和可选覆盖层，适合微动作状态。
- `keyframes`：3–6 个语义明确的关键姿势加程序化时间曲线，适合交互动作。

### 状态分配

| 状态 | 目标表达 | 说明 |
| --- | --- | --- |
| idle | pose | 标准正面底图、随机眨眼、呼吸、轻微歪头、尾巴摆动 |
| focus | pose | 标准底图；眼镜为独立 overlay |
| sleep/rest/tired/sulk/curious | pose 或少量 keyframes | 保持脸与身体不重绘；Zzz/问号独立绘制 |
| cheer/greet/petted/stretch/drink/grabbed | keyframes | 每个动作 3–6 个明确关键姿势；爱心、水碗、水滴等独立分层 |
| walk/run | sequence | 从受控图生视频或严格关键步态中选取一个完整周期 |

## 迁移顺序

1. 完成 idle 的最小闭环：标准底图、眨眼、呼吸、尾巴和轻微歪头。
2. 将眼镜、爱心、Zzz、问号、水碗和水滴从角色图中拆成独立道具或程序特效。
3. 扩展声明式动画 manifest，并兼容旧 sequence。
4. 用少量关键姿势迁移 cheer、greet、petted，验证后再迁移其余交互状态。
5. 单独实验 walk/run：使用标准右侧 reference、固定机位、原地步态、纯色背景的受控图生视频，抽取一个完整周期；只有质量优于旧序列才替换。

每一步必须可独立运行和回退。不得以一次性重写播放器为前置条件。

## AI 资产生成约束

每次生成只处理一个状态或一个相邻关键姿势。输入中同时提供角色 reference 与上一姿势；提示词明确“只改变姿态”。固定以下不变量：

- 同一只狗的脸型、眼距、鼻口比例、耳朵形状、毛色和卷毛密度；
- 身长、腿长、爪子大小和尾巴形状；
- 固定正交或弱透视机位、固定光照和材质；
- 不添加未要求的项圈、衣物、花纹或道具；
- 纯色可抠除背景，主体与边缘留足安全距离；
- walk/run 统一朝右并原地运动，画面中不得前进或缩放。

复杂毛发透明边缘优先使用纯色背景加本地抠图。生成结果不得未经检查直接进入 `src/assets`。

## 连贯性验收

动画通过验收必须同时满足以下条件：

### 自动检查

- 文件数、尺寸、透明通道和 manifest 引用完整；
- 所有帧共用画布，主体不触边；
- 身体前景面积相对中位数偏差不超过 12%，刻意 squash/stretch 除外；
- 脸部区域或人工锚点的帧间位移不超过目标显示尺寸的 3%；
- 相邻帧轮廓差异不得出现孤立尖峰；
- 循环动画最后一帧到第一帧的差异不显著高于普通相邻帧；
- 道具的存在性、位置和尺寸符合状态约束。

### 动态目检

- 必须生成真实播放 FPS 的循环 GIF/WebP 或应用内预览，至少连续观察三个循环；
- 同时以 0.5 倍速检查脸、四肢、耳朵、尾巴和道具；
- 不得只凭 contact sheet 或单帧美观判定通过；
- walk/run 需检查落脚顺序、支撑相位、腾空相位、身体速度与窗口位移是否协调；
- 发现身份漂移、肢体增生、闪烁或首尾跳变时，返工源关键姿势，不使用插帧掩盖。

### 人工放行

idle 完成后作为方案闸门。若其稳定性和生命感不优于现有 16 帧 idle，则暂停后续迁移并调整资产分层；不得机械推进第 2–5 步。

## 工程约束

- 保持透明窗口、像素级命中和常驻 CPU 目标不退化；
- 静止或低频状态不得引入高频 React 重渲染；
- 动画时钟集中管理，优先 `requestAnimationFrame` 配合时间戳，而非为每层创建独立定时器；
- 装饰层默认不参与宠物本体命中，交互道具可显式选择是否参与；
- 原始 reference、关键姿势和生成参数保存在 `assets-src`，运行时优化产物保存在 `src/assets`；
- 资产更新同时更新 evergreen feature spec，proposal 只记录本次设计决策。

## 提交策略

关键节点提交，避免按文件或小修正频繁提交：

1. proposal；
2. idle 闸门通过；
3. 声明式运行时与道具分层完成；
4. 关键姿势状态完成；
5. walk/run 实验与最终规格更新。

## 非目标

- 不恢复 Cubism/Live2D 编辑工作流；
- 不在本轮引入完整 3D 四足绑定；
- 不强制所有状态拥有相同帧数或 FPS；
- 不因为新方案存在而删除尚未完成迁移的旧序列。
